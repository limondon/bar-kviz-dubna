# Локальные исправления — 13–19 сентября 2026

Сохранён единый вход персонала. Официант, бармен и менеджер — переключаемые рабочие режимы существующего аккаунта; отдельных логинов не требуется. Это не разграничение полномочий между сотрудниками общего аккаунта.

## Что изменено

- Создание заказа, расчёт цены, списание остатков, номер и квитанция повторного запроса перенесены в серверные Firebase Functions и общую транзакцию RTDB. Повтор запроса после потери ответа возвращает прежний результат.
- Гостям закрыта прямая запись заказов, остатков и вызовов, чтение приватных данных и токенов. Сервер проверяет стол, сессию, срок QR, товар, количество, опции и итог.
- Исправлены платные добавки и итог корзины; доступны разные варианты одного напитка. Незавершённая отправка восстанавливается после перезагрузки, включая получение квитанции уже закрытого стола.
- Редактирование сохраняет цены и статусы; конфликты версии отклоняются. Удаление возвращает только неиспользованные остатки, повтор удаления не увеличивает склад.
- Выдача и журнал доставки сохраняются вместе. Исправлены закрытие/повторное открытие столов, пробковый сбор в смешанных заказах, пустые открытые столы и сохранение склада при правке меню.
- QR квиза ограничены по времени и отзываются при завершении. Удалены автоматические очистки данных при запуске.
- Корзина прокручивается в горизонтальной ориентации и на узком экране; улучшены подписи, клавиатурное управление, масштабирование и режим уменьшенной анимации.
- Гостевая авторизация изолирована от входа персонала. На localhost используются только эмуляторы demo-проекта.

## Локальный запуск интеграции

1. Подготовить Node.js 22 и Java 21. В текущем Windows-worktree переносимые версии находятся в игнорируемой папке .local-tools/runtime; системные версии не менялись.
2. Выполнить `npm ci`, `npm ci --prefix functions` и `npm install --prefix .local-tools/firebase-cli firebase-tools@15.30.1 --ignore-scripts --no-audit --no-fund`.
3. Для автоматического прогона выполнить `npm run test:integration`. Он запускает эмуляторы, подготавливает тестовые данные и аккаунты, выполняет проверки и останавливает эмуляторы. Данные demo-базы сбрасываются перед каждым сценарием.
4. Для ручной работы выполнить `npm run emulators`, раздавать корень проекта локальным HTTP-сервером и открыть localhost. Подготовить `live/schemaVersion = 2`, тестовое меню в `live/menu2` и общий аккаунт персонала manager@1708.local в Auth Emulator. Отдельные аккаунты ролей не нужны.

Запуск через scripts/run-integration.cjs фиксирует demo-проект и DATABASE_URL, чтобы клиент, правила и Functions обращались к одному namespace demo-bar-1708-default-rtdb. Без этой настройки CLI 15 по умолчанию направлял Functions к другой пустой demo-базе. Интеграционный тест отказывается запускаться с другим проектом или внешними адресами Auth/Database. Все три эмулятора слушают 127.0.0.1. Порядок установки эмуляторов описан также в [официальной документации Firebase](https://firebase.google.com/docs/emulator-suite/install_and_configure).

Порты заданы в firebase.json: Auth 9099, Database 9000, Functions 5001. Для браузерных тестов с установленным Edge задать `PLAYWRIGHT_EXECUTABLE_PATH` на его исполняемый файл.

## Продолжение исправлений

- Возврат заказа в очередь теперь использует серверную операцию с проверкой исходного статуса. Убирается дата завершения заказа; даже старые выданные позиции без флага stockConsumed помечаются использованными, чтобы последующее удаление не вернуло их на склад.
- Подтверждение гостевого заказа сохраняется в sessionStorage и восстанавливается при обновлении. «Заказать ещё» заново проверяет действительность сессии.
- Service Worker обрабатывает только известные локальные GET-ресурсы. При отсутствии сети параметры QR не мешают получить сохранённую страницу; отсутствующий ресурс возвращает явный 503. Чужие кэши не удаляются, новый worker не подменяет код во время активной работы. Полная работа без сети по-прежнему не обеспечена: внешние Firebase SDK требуют отдельной проверки и стратегии поставки.
- Добавлены проверки этих случаев: три изолированных теста обработчика Service Worker, регрессия возврата использованного остатка и браузерный сценарий сохранения подтверждения.

## Редактор товара: параллельные изменения

Карточка товара сохраняется относительно снимка меню при её открытии. Полученные за это время обновления Firebase больше не подменяют базовую версию формы. Неизменённый остаток берётся с сервера; явно изменённый остаток при конфликте отклоняется. Перестановка или изменение меню другим устройством также отклоняет устаревшую карточку. До подтверждения локальное рабочее меню не изменяется; ошибка показывается внутри карточки с сохранением введённых значений. Повторное нажатие сохранения во время запроса блокируется.

Добавлены три браузерные регрессии для этих случаев. Дополнительно сервер отклоняет использование номера уже выполненной операции персонала для другого действия (отдельная Node-проверка). Удалены неиспользуемые импорты прежнего клиентского списания склада из основных модулей; действующие операции заказов используют сервер.

Общий редактор категорий и поля таблицы меню также переведены на отдельные копии: добавление, удаление, скрытие, перестановка и изменение полей не меняют рабочее меню до ответа сервера. Снимок относится к показанному редактору; подтверждение удаления категории сохраняет именно тот снимок, по которому открыто окно. Ошибка выводится в редакторе, неподтверждённые изменения не попадают в следующую операцию. Во время сохранения повторные операции блокируются. При вводе в поле обновления остатков не перерисовывают форму.

Удалено автоматическое заполнение пустой базы встроенным меню при старте. Пустой загруженный каталог отличается от ещё не загруженного, в том числе в выборе товаров и расчёте цен. После удаления всех категорий можно создать новую без восстановления старого ассортимента. Для новой пустой базы меню теперь нужно подготовить явно через интерфейс или импорт тестовых данных.

Проверены сбой удаления с последующим сохранением другого поля, сбой перестановки категории, конкурирующая корректировка остатка во встроенном поле, удаление всего каталога с перезагрузкой и создание новой категории. Серверное сравнение версий теперь не зависит от порядка ключей JSON-объектов, но продолжает учитывать порядок категорий и товаров. Добавлена отдельная регрессия на это сравнение.

Браузерный стенд при перезагрузке теперь отдаёт актуальное тестовое состояние сервера вместо исходного снимка. Это уточняет проверку восстановления страниц; реальный Firebase по-прежнему не используется.

## Повторная отправка персоналом и старые записи

После отправки форма персонала блокирует изменение стола, позиций, примечания и приоритета до подтверждения результата. При потере ответа остаётся кнопка «Проверить отправку». После перезагрузки восстанавливаются тот же запрос и его поля; повтор возвращает ранее созданный заказ. Явный отказ в проверке данных разблокирует форму для исправления. Повреждённый локальный черновик больше не останавливает загрузку приложения. Если браузер не позволяет сохранить идентификатор запроса, новый заказ не отправляется: интерфейс сообщает причину.

Для чтения старых текстовых заказов снято ограничение 99 на строку, введённое для новых заказов; сохраняются исходные положительные целые количества. Нечитаемые записи изолируются при загрузке: остальные заказы продолжают отображаться, а над рабочими экранами появляется предупреждение о неполной очереди и суммах с ключами проблемных записей. Никакого удаления или автоматической перезаписи исходных данных не выполняется. Это обработка чтения; полноценная миграция старого текстового формата в структурированные позиции остаётся отдельной работой.

Добавлены четыре браузерных сценария: потеря принятого ответа персоналом и перезагрузка, исправление отклонённого заказа, частично повреждённые старые данные, некорректный сохранённый черновик.

## Границы сессий стола

- Сервер проверяет открытую текущую сессию при изменении статусов и редактировании позиций заказа. Закрытый чек сначала требуется явно переоткрыть для исправлений; заказ предыдущих гостей не меняется через текущую сессию.
- Заметки и отметка «вбили в систему» переведены с прямой записи на updateStaffTableDetails: проверяются сессия, состояние стола и предыдущее значение поля. Время отметки задаёт сервер. Клиент показывает успех после подтверждения. При конфликте заметка остаётся в открытом окне; повтор после потери ответа использует прежний номер операции.
- Окно пробкового сбора сохраняет дату и сессию при открытии. Совпадения старых количеств недостаточно, чтобы применить сбор к новым гостям.
- При создании новой сессии очищаются заметка и отметка учёта предыдущих гостей. Явное переоткрытие того же чека сохраняет его данные.
- Удаление текущей сессии сохраняет метаданные предыдущих закрытых сессий, пока для них существуют заказы. Архивные чеки продолжают отображаться.

Добавлены пять серверных регрессий и пять браузерных сценариев. Чтение метаданных для отображения больше не создаёт фиктивный локальный стол: новый стол со сбором открывается только серверной операцией. Нужна совместная публикация обновлённого клиента и Functions, включая новую функцию updateStaffTableDetails. Реальные интеграционные ограничения проверки остаются прежними.

## Постоянная связь заказа с товаром

При сохранении меню сервер назначает товарам productId. Переименование, перестановка и редактирование сохраняют идентификатор; новый товар получает новый идентификатор, даже если использует прежнее название. Переданное клиентом значение productId не заменяет существующую идентичность.

В той же транзакции существующие структурированные позиции заказов связываются с товарами по однозначному исходному соответствию. Название и сохранённая цена в чеке остаются прежними. Новые заказы персонала и гостей сохраняют идентификатор из каталога. Возврат склада и поиск товара для действий над позицией используют идентификатор, если он известен, и не переключаются на одноимённый другой товар.

Удаление товара с незавершёнными структурированными позициями отклоняет всё сохранение меню. Для незавершённого старого текстового заказа также отклоняются затрагивающие его переименование и удаление: автоматическое преобразование такого формата не выполняется. Для ранее повреждённых/неоднозначных связей и исчезнувших товаров нужна отдельная проверка данных.

Гостевая корзина сохраняет идентификатор выбранного товара. Замена товара на другой с теми же названием, ценой и индексом требует выбрать позицию заново. При первом назначении идентификаторов открытые старые корзины также могут потребовать повторного выбора; уже принятые операции возвращают прежние квитанции.

Добавлены шесть серверных регрессий и два браузерных сценария: переименование/перестановка с возвратом, повторное использование старого имени, удаление зарезервированного товара, сохранение идентичности, подмена товара в гостевом запросе и защита старого текстового заказа.

## Вызовы официанта и квиз — 15 сентября

Вызов принадлежит конкретной сессии. При закрытии или смене сессии старые ожидающие вызовы отменяются сервером; новый вызов новых гостей не объединяется со старым. Интерфейс и уведомления учитывают актуальность сессии. Отметка «Подошёл» выполняется сервером и не воссоздаёт уже удалённый вызов. Повтор после потери ответа возвращает прежний результат.

Кнопка очистки теперь удаляет только выбранные завершённые вызовы и вызовы старых сессий, максимум 1000 за один запрос. Ожидающие актуальные и пришедшие после открытия подтверждения вызовы сохраняются. Гостевой запрос вызова также сохраняет свой номер до подтверждения: повтор не звонит заново, даже если официант уже обработал первый вызов.

Подготовка квиза перенесена в атомарную серверную операцию prepareStaffQuiz. Она берёт актуальные данные столов, сохраняет сессии, заметки и отметки уже открытых столов; для закрытых создаёт новые сессии без данных прежних гостей. Все 19 кодов и состояние квиза сохраняются вместе. Повтор неопределённой подготовки использует тот же номер запроса и возвращает тот же набор QR; ранее заменённый или отозванный набор не выдаётся как действующий.

Завершение через finishStaffQuiz проверяет идентификатор квиза, запомненный до подтверждения. Старое окно не может отозвать новые QR. Сервер по-прежнему отклоняет новые заказы из уже открытых страниц с отозванным кодом.

Добавлены пять серверных регрессий и пять браузерных сценариев, уточнена статическая проверка доступа к config/quizSession. Печатное окно в браузерном тесте заменено заглушкой: проверены состав переданных данных и восстановление набора токенов, но не отрисовка QR библиотекой, принтер или камера. Новые функции и правило чтения состояния квиза требуют согласованной публикации с клиентом.

## Гостевая корзина после отказа — 15 сентября

Если сохранённый запрос после перезагрузки явно отклонён сервером, клиент заново проверяет сессию, загружает каталог и подключает обновления меню. Корзина, варианты и примечание сохраняются; цены того же товара обновляются, количество можно исправить и отправить новый запрос. Сообщение о причине отказа остаётся в корзине. Если стол закрыт или ссылка недействительна, показывается соответствующий экран; при ошибке сети предлагается обновить страницу, черновик сохраняется.

Пока результат отправки неизвестен, показанная сумма и примечание соответствуют сохранённому запросу: обновления каталога не меняют сумму, примечание доступно только для чтения. Во время запроса и восстановления редактирование и повторный запуск отправки блокируются независимо от перерисовки экрана. Получение ранее принятого заказа после закрытия стола сохранено.

Исправлен также таймер переходов: быстрый возврат из корзины больше не скрывает уже активное меню. Добавлены пять браузерных регрессий: изменение цены после перезагрузки, исправление количества и последующее обновление каталога, неизменность неопределённого запроса, отказ закрытого стола и быстрые переходы между экранами. Service Worker обновлён до bar-v30. Проверки используют прежний изолированный стенд; публикация и проверка на реальном Firebase не выполнялись.

## Отложенные заказы и архивные чеки — 15 сентября

Новый запрос персонала сохраняет московскую дату, идентификатор и состояние сессии стола. Сервер сравнивает их с актуальными данными до создания заказа, открытия стола, изменения счётчика и склада. После закрытия, замены сессии или смены даты непринятый старый запрос отклоняется. Поля разблокируются с сохранением текста для проверки сотрудником. Если запрос уже был принят, повтор возвращает исходную квитанцию, даже после смены гостей. До первой загрузки столов отправка запрещена.

Кнопки переоткрытия в обоих списках передают идентификатор конкретного чека. Архивный чек прежней сессии не переоткрывает нынешнюю сессию и не меняет её QR; сервер отклоняет несовпадение. Уже открытый стол нельзя переоткрыть новым запросом и случайно сменить токен. Повтор после потери ответа в открытой странице использует прежний идентификатор операции. Переоткрытие последней закрытой сессии остаётся доступным; восстановление более ранней сессии поверх новых гостей не реализовано. Закрытие также запоминает сессию до окна подтверждения.

При восстановлении обычного гостевого черновика повреждённые строки отбрасываются с предупреждением, корректные позиции и примечание сохраняются. Повреждённая неопределённая отправка или нечитаемая сохранённая запись не удаляется автоматически: показывается просьба уточнить принятие заказа у официанта. Если браузер не позволяет сохранить номер нового запроса, заказ и вызов официанта не отправляются. Добавлены три Node-регрессии и семь браузерных сценариев. Service Worker обновлён до bar-v31.

## Фоновая доставка уведомлений — 20 сентября

Добавлена стандартная Web Push-подписка для установленного PWA. Устройство регистрируется серверной функцией, endpoint и ключи закрыты правилами RTDB от чтения и записи из браузера. Выбранная роль определяет события: бармен получает новые заказы, официант — вызовы гостей, менеджер — оба типа. Отдельные аккаунты не добавлялись. Отключение уведомлений удаляет серверную подписку; ответы 404/410 от push-службы автоматически очищают устаревшие устройства.

Новый заказ или вызов создаёт короткую запись в `pushOutbox` в той же атомарной транзакции. Повтор уже принятой операции не создаёт второе событие, а импорт старой истории не запускает массовую рассылку. При временном отказе Apple или браузерной push-службы сервер сохраняет событие, запоминает уже доставленные устройства и повторяет оставшиеся. Уведомление содержит только номер заказа и стол, без состава заказа и примечания. Service Worker обновлён до `bar-v35`.

Сгенерированная пара VAPID хранится только в исключённом из Git каталоге `.release`; для эмулятора создан отдельный игнорируемый файл. Перед публикацией оба значения нужно интерактивно сохранить как `WEB_PUSH_PUBLIC_KEY` и `WEB_PUSH_PRIVATE_KEY` в Firebase Secret Manager. Локально прошли проверки валидации подписок, ролей, очистки просроченного устройства, приватности содержимого и серверной регистрации. Реальную доставку через Apple Push Notification service можно окончательно подтвердить только после публикации на физическом iPhone с iOS 16.4+.
