# Перенос на хранение v2

Рабочая база в этой задаче не изменялась. Публиковать только фронтенд или только правила нельзя: версия v2 требует согласованного переноса данных, Functions и клиента.

## Что меняется

- `live/` — меню, заказы открытых сессий, метаданные столов, счётчик, настройки, вызовы и недавние подтверждения операций. Транзакции выполняются только здесь.
- `archive/days/YYYY-MM-DD/` — закрытые заказы и снимки метаданных столов. Чеки сохраняются с исходными позициями, ценами, суммами и примечаниями сразу после закрытия.
- `archiveOperations/` — старые подтверждения запросов, необходимые для безопасного повтора после потери ответа. Не удалять эту ветку по возрасту.
- `archive/maintenance/` — сохранённые старые служебные записи.
- `live/maintenance` — атомарная блокировка новых операций на время обслуживания. Включается и выключается менеджером из настроек.

При закрытии счета сервер сразу переносит всю сессию стола: все позиции должны быть выданы, а сохранённые цены и суммы — корректны. Сначала записывается и подтверждается точная архивная копия, затем совпадающие заказы удаляются из `live`. Переоткрытие возвращает тот же снимок в `live` одной транзакцией и только после успешного открытия удаляет архивный дубль. Повтор с тем же `requestId` завершает прерванный шаг без второго списания или второго счёта.

`archiveOldOrders` запланирована на 06:00 по Москве ежедневно. Она переносит оставшиеся закрытые счета старой версии независимо от возраста, а затем убирает служебные записи и метаданные старше 30 дней. Открытые, текстовые и повреждённые заказы остаются в `live`. Обычный пакет содержит до 500 заказов; большой единый счёт переносится целиком. Один запуск обрабатывает максимум 40 пакетов каждого типа, оставшееся — в следующий запуск.

На время каждого пакета сервер устанавливает `live/archivePending`. Сначала сохраняется архивная копия, затем в транзакции удаляются совпадающие рабочие записи и увеличивается `archiveEpoch`. При сбое пакет повторяется с тем же идентификатором. Следующий запрос или запуск архива возобновляет незаконченный пакет. Запрос, столкнувшийся с переносом, может получить временную ошибку и должен повторяться с прежним `requestId`.

Все записи из браузера запрещены правилами, включая записи общего аккаунта персонала. Действия интерфейса выполняются через Functions. Общий логин и переключение ролей сохранены.

После первого перехода на v2 режим обслуживания останавливает новые заказы, изменения столов и меню, ручной и плановый архив. Его включение выполняется транзакцией по тому же рабочему разделу, поэтому после подтверждения новый запрос не может завершиться за блокировкой. Повтор операции, принятой до включения режима, по-прежнему возвращает сохранённый результат. Просмотр очереди, чеков и статистики остаётся доступен. Включить или выключить режим может менеджер через пункт «Режим обслуживания»; активное состояние видно на постоянной красной панели.

Для самого первого переноса со старой структуры эта кнопка ещё недоступна и не заменяет остановку записей на уровне инфраструктуры в шаге 2.

## Подготовка на локальном экспорте

Предварительный полный экспорт рабочей RTDB от 20 сентября проверен локально и хранится в исключённом из Git каталоге `.release`: он содержит данные гостей, заметки и токены. Экспорт снимался без остановки приёма заказов, поэтому годится для аудита и репетиции, но не для итогового импорта. Во время окна публикации обязателен новый экспорт после остановки записей.

```powershell
npm run audit:data -- --input export.json --output audit.json
npm run prepare:storage -- --input export.json --output migrated.json --report migration-report.json
npm run verify:storage -- --source export.json --migration migrated.json --migration-report migration-report.json --output verification.json
npm run test:rehearsal -- migrated.json
```

Обе команды работают с локальными файлами и не обращаются в Firebase. Исходный файл не меняется; существующие выходные файлы не перезаписываются. `prepare:storage` создаёт полный подготовленный экспорт, переносит все корректные завершённые закрытые счета независимо от даты и сохраняет неизвестные корневые разделы. В отчёте — числа заказов, проблемы исходных данных и SHA-256 сериализованного JSON до/после (это не хеш исходного файла с его форматированием). Повторный перенос уже подготовленного экспорта отклоняется.

`verify:storage` заново запускает аудит исходника и независимо проверяет хеши исходника и результата, наличие каждого исходного заказа ровно в одном месте, неизменность снимков, архивные суммы, остатки, идентификаторы товаров и точное восстановление исходного экспорта через откат. Поэтому замечания нельзя скрыть редактированием migration-report. Команда завершается ошибкой при любом нарушении и не перезаписывает существующий отчёт.

Проверить отчёт: число архивных плюс оставшихся заказов должно равняться исходному. Проблемные цены нельзя автоматически заменить текущими ценами меню. Они требуют отдельной проверки; до неё соответствующий стол остаётся в рабочем разделе.

В предварительном рабочем экспорте найдено 393 заказа. Проверка целостности не обнаружила потерь, изменений или дублей: 11 полностью подтверждённых закрытых заказов подготовлены к архиву, 382 сохранены в `live`. Зафиксировано 1380 замечаний к старым полям: отсутствуют исторические снимки цены, итоговой суммы или идентификатора товара. Это пробелы старого формата, а не повреждение переноса. Подставлять сегодняшние цены в историю нельзя. Размер подготовленного рабочего набора около 246 КБ, поэтому сохранение этих записей не создаёт текущей проблемы объёма.

Репетиция на этой подготовленной копии в Firebase Emulator сохранила все 382 старых заказа без изменений, создала 6 параллельных заказов с 6 уникальными номерами и подтвердила блокировку нового заказа режимом обслуживания. Прогон занял 10,9 секунды на локальном стенде; это проверка корректности, а не замер облачной мощности.

Прогнать `npm test`, `npm run test:mobile`, `npm run test:integration`, `npm run test:load`. Для мобильного набора установить движки командой `npx playwright install chromium webkit`. Эмуляторные наборы запускаются по очереди, поскольку используют одинаковые порты.

## Порядок публикации

1. Выбрать окно без обслуживания. Сохранить текущий комплект клиентских файлов, Functions, правил и настройки доступа. Фактический Firebase-проект уже определён по действующей конфигурации и подтверждён чтением базы; перед выпуском его ID всё равно вводится дважды в предрелизной проверке.
2. Остановить приём запросов старой версией: закрыть доступ к записям RTDB и к изменяющим Functions на уровне инфраструктуры, приостановить задания. Одних правил недостаточно: Admin SDK обходит правила. Дождаться завершения уже выполняющихся функций. Сохранить настройки доступа для последующего восстановления.
3. Сделать полный резервный экспорт после остановки записей. Проверить, что файл читается, сохранить отдельно. Подготовить v2 именно из этого свежего экспорта; более ранний пробный файл не импортировать.
4. Собрать сайт командой `npm run build`. Firebase Hosting настроен только на `dist`; сборщик использует белый список и проверяет, что Service Worker не ссылается на отсутствующий файл.
5. Создать итоговый блокирующий отчёт, дважды явно указав фактический Firebase project ID и число замечаний из проверенного отчёта аудита:

```powershell
npm run preflight:release -- --project ФАКТИЧЕСКИЙ_PROJECT_ID --confirm-project ФАКТИЧЕСКИЙ_PROJECT_ID --source export.json --migration migrated.json --migration-report migration-report.json --accept-audit-issues ЧИСЛО --output release-preflight.json
```

Команда отклоняет demo-проект, несовпадающий ID, изменённую базу, непросмотренное число замечаний, неполный Firebase-конфиг и содержимое `dist`, отличающееся от белого списка. В отчёте сохраняются отпечатки базы, клиентского комплекта и серверного кода, а также точная команда публикации. Она сама ничего не публикует.

6. Импортировать подготовленный экспорт в согласованную базу. Проверить `live/schemaVersion = 2`, количество и суммы заказов, остатки, счётчик, несколько архивных чеков и наличие подтверждений операций.
7. Непосредственно перед публикацией повторить ввод project ID и заново сверить пломбу выпуска с текущими файлами:

```powershell
npm run verify:release -- --preflight release-preflight.json --project ФАКТИЧЕСКИЙ_PROJECT_ID --confirm-project ФАКТИЧЕСКИЙ_PROJECT_ID --source export.json --migration migrated.json --migration-report migration-report.json --accept-audit-issues ЧИСЛО
```

Команда заново выполняет все проверки предрелизного барьера и сравнивает контрольные суммы базы, `dist`, Functions и правил с сохранённым отчётом. Если после создания отчёта изменился хотя бы один вход, выпуск блокируется и требуется новый `release-preflight.json`.

8. До публикации сохранить подготовленные Web Push-ключи из закрытого файла `.release/web-push-keys.json` в Secret Manager фактического проекта. Значения вводятся интерактивно и не должны попадать в командную строку, Git или отчёты:

```powershell
firebase functions:secrets:set WEB_PUSH_PUBLIC_KEY --project ФАКТИЧЕСКИЙ_PROJECT_ID
firebase functions:secrets:set WEB_PUSH_PRIVATE_KEY --project ФАКТИЧЕСКИЙ_PROJECT_ID
```

9. Опубликовать одним согласованным комплектом Functions, правила и Hosting из `dist`, включая `js/archive.js` и `sw.js` версии `bar-v35`. Использовать только project ID и команду, которую только что вывела `verify:release`. Закрыть старые вкладки на устройствах персонала и обновить установленное приложение. Старые корневые пути намеренно закрыты правилами.
10. Восстановить необходимый доступ к новым функциям и включить расписание. Проверить успешный запуск `archiveOldOrders` в Cloud Scheduler и его журналы; отслеживать ошибки, зависший `archivePending` и `pushOutbox`. Расписание локальный эмулятор не исполняет, тесты вызывают тот же код через служебную функцию.
11. На Android и iPhone проверить открытие QR, один заказ, выдачу, закрытие стола, просмотр архива, потерю связи и повтор без дубля. На iPhone с iOS 16.4+ добавить сайт на экран «Домой», открыть его с иконки, включить уведомления и проверить новый заказ при закрытом PWA. Отдельно проверить вызов официанта, камеру, печать QR, реальную экранную клавиатуру и возврат после блокировки телефона.

Firebase создаёт расписание при публикации scheduled function; проекту требуется Cloud Scheduler API. Основа конфигурации: [официальная документация Firebase](https://firebase.google.com/docs/functions/schedule-functions).

## Откат

Если после перехода новые записи ещё не принимались, в том же окне обслуживания можно восстановить согласованный резервный комплект кода, правил и базы.

Если новые заказы уже появились, старый резервный экспорт нельзя просто импортировать: это потеряет новые заказы. В исправном интерфейсе менеджера включить режим обслуживания и дождаться красной панели; при недоступности приложения остановить записи и задания на уровне инфраструктуры. Завершить незаконченный пакет архива до включения режима, выгрузить свежую v2-базу и подготовить обратный перенос:

```powershell
npm run prepare:storage -- --rollback --input fresh-v2.json --output rollback.json --report rollback-report.json
npm run verify:rollback -- --source fresh-v2.json --rollback rollback.json --rollback-report rollback-report.json --output rollback-verification.json
```

Первая команда объединяет рабочие и архивные записи, сохраняет новые заказы и отказывается продолжать при конфликтующих заказах, незавершённом переносе или неизвестных рабочих разделах. Вторая независимо пересчитывает контрольные суммы, проверяет каждый заказ и требует точного совпадения всего восстановленного экспорта. Только после успешной проверки восстанавливать код, правила и структуру базы согласованно. Любой ручной конфликт разобрать до снятия окна обслуживания.

## Границы проверки

Архив не участвует в обычных транзакциях, но объём `live` всё ещё влияет на нагрузку. Нагрузочный прогон проверяет 5000 архивных заказов и компактизацию 2000 закрытых заказов текущего дня. Предварительный рабочий экспорт проверен только чтением и на локальном эмуляторе; свежий снимок после остановки записей, импорт, облачное расписание, резервное копирование, доставка Web Push через Apple/браузер и физические телефоны пока не проверены. Большое число одновременно открытых или повреждённых записей и работа нескольких облачных экземпляров требуют отдельных измерений.
