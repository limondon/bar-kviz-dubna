# Передача стола на Эвотор: тестовая версия 0.2

## Что реализовано локально

- В открытом посещении стола у менеджера/официанта есть «Передать на кассу · тест». Предпросмотр показывает каждую исходную строку с количеством и ценой; кружки исключаются. Старые строки без сохранённой цены используют однозначную текущую цену меню с предупреждением. Отсутствующая/неоднозначная цена блокирует отправку.
- Снимок хранится в `config/evotor/v1/transfers/YYYY-MM-DD/SHA256(date,table,sid)`. Доступ уже ограничен действующими правилами `config` — сотрудником `manager@1708.local`. Гостевые права не расширяются. Изменения заказов, остатков и оплаты этот модуль не выполняет.
- Один слот на посещение: повтор до открытия обновляет состав; после начала открытия повтор блокируется, даже если появились дозаказы. Исходные строки, варианты и сохранённые цены не объединяются по усечённому названию.
- На кассе отдельный экран входа сотрудника, список по выбранной дате (по умолчанию текущая), обновление каждые 10 секунд только на открытом экране списка. Пароль и токены только в памяти. После перезапуска/пересоздания Activity нужен повторный вход. Переход даты через полночь вручную; вчерашний стол передаётся с его исходной датой.
- Каждая строка явно сопоставляется с UUID карточки кассы; выбор сохраняется на этом устройстве. Ключ включает полный вариант названия, цену и menuItemId/productId, если исходный заказ его содержит. Старые заказы не имеют стабильного ID меню, поэтому совпадение имени не используется для автоматического выбора. Кассир отвечает за выбор смыслово правильной карточки. Цена сайта и кассы должна совпадать; тип/налог/название повторно проверяются.
- Перед открытием читаются метаданные посещения и заказы **только выбранного дня**, проверяется весь состав, включая новые заказы и добавленные строки. Непустой чек, отсутствующая карточка, изменение цены/состава, неизвестный или маркированный тип блокируют действие. Снимок действителен 15 минут; обновить можно на сайте до открытия.
- Для запроса по дате локально добавлен только индекс `orders/.indexOn = ["date"]`. Права чтения/записи не меняются. **Индекс в рабочую базу не применён.** Без него REST-запрос может быть отклонён; это ошибка проверки, чек не откроется.
- Резервирование перед SDK: Firebase REST ETag + conditional PUT всего дня. Две кассы не могут успешно зарезервировать один снимок. Пересечение исходных заказов с другой начатой передачей блокирует повтор после переименования стола, даже если ID строк пересозданы. Обычные повторы записи при потере подтверждения используют прежний слот.
- До единственного вызова SDK попытка синхронно записывается в локальный журнал. Нет автоматического повтора команды при таймауте, перезапуске или потере сети. Результат сначала сохраняется локально, затем подтверждается на сайте; несинхронизированные подтверждения повторяются при обновлении списка. Уже подтверждённая история не перечитывается при каждом обновлении.
- Статусы передачи: queued → opening → opened / rejected / unknown. Это состояния интеграции, не приготовления/выдачи/оплаты. `opened` означает открытый чек, **не оплату**. SDK-команды оплаты/печати отсутствуют, сайт автоматически стол не закрывает.

## Границы первого теста

- Это snapshot-интеграция. Изменение заказа сразу после финальной проверки может опередить открытие SDK: единой транзакции между Firebase и физической кассой нет. Во время проверки и открытия сотрудник не должен параллельно редактировать этот стол. Просмотр состава и суммы обязателен.
- Дозаказ **после попытки открытия**, частичная оплата, разделение счёта, повтор после ручной отмены чека и автоматическое подтверждение оплаты ещё не реализованы. Повтор целого посещения блокируется, чтобы не пробить ранее переданные строки второй раз. Такие случаи пока ведутся вручную; обход блокировки и удаление записей передачи запрещены.
- При unknown/opening в локальном журнале новые открытия блокируются до выяснения результата. Автоматического сброса или небезопасной кнопки «Повторить» нет. Поздний успешный ответ заменяет unknown на opened. При потерянном окончательном ответе нужна ручная сверка и отдельная процедура восстановления; не очищать данные приложения для обхода защиты.
- Пустой список, ошибка сети и отказ доступа различаются. Автономный экран 0.1 остаётся доступен, с прежней однократной блокировкой.
- Алкоголь/маркировка в реальном фискальном сценарии не проверены. Прототип не подменяет специальный тип товара универсальным SERVICE/NORMAL.
- Никаких новых серверов/платных подписок не требуется для этой реализации. Доступность Firebase в заведении, фактические задержки и условия постоянного распространения Эвотора требуют отдельной проверки.

## Следующая проверка вне обслуживания гостей

1. Отдельно согласовать установку APK 0.2 через тестовую версию Эвотора, публикацию сайта и применение индекса. Текущая работа не делает ни одно из этих действий; публичное ревью/магазин также не запускаются.
2. На изолированных тестовых данных проверить стол с несколькими товарами и разными ценами/количествами. Войти существующей учётной записью сайта на кассе, выбрать правильную дату, сопоставить поддерживаемые карточки. Не вводить пароль от кабинета Эвотора вместо пароля сайта.
3. До подтверждения проверить чек кассы: он должен быть пуст. Отправить состав, открыть один раз, сверить все строки, цены и итог. Не оплачивать; очистить стандартными средствами кассы и проверить пустой чек.
4. Повторный тап, вторая касса, переименование стола, разрыв сети, перезапуск, дозаказ до открытия и закрытие стола должны либо корректно обновить снимок до резервирования, либо заблокировать открытие с объяснением. При неизвестном результате проверить текущий чек, не переустанавливать приложение и не сбрасывать журнал.

## Локальная проверка

`npx playwright test tests/cash-transfer.spec.js` — браузерный сценарий с изолированным Firebase. Существующая очередь/столы/статистика проверяются отдельными тестами репозитория.

`integrations/evotor/scripts/build.ps1` — JUnit (включая настоящий wire fixture из JS), Android Lint, APK. Сценарии: потерянное подтверждение, конкурирующий ETag, переименование/пересечение строк, поздний ответ, порча снимка, изменение/удаление/дозаказ, истечение срока, выход из аккаунта. HTTP transport подменён тестовым backend; живой Firebase и физическая касса в этих проверках не используются.

Общий fixture: `fixtures/bill.json`, генератор `scripts/evotor-contract-fixture.cjs` из корня сайта. Изменение JS-контракта должно сохранить соответствие Java-тесту.
