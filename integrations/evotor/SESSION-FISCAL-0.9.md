# Сохранение входа и проверка фискальных документов — 0.9

## Проблемы на установленной 0.8

Фото пользователя подтверждают: после «Удалить чек» продолжение блокируется сообщением «Не удалось проверить фискальные документы»; после возврата через Android Home и запуска приложения вновь требуется пароль.

В 0.8 все данные авторизации хранились в памяти экземпляра BridgeClient, onCreate всегда показывал вход, а onDestroy вызывал logout. Запуск из MainActivity создавал ещё один TransferActivity. Исправление: переиспользование Activity (singleTask), восстановление сеанса при создании и отсутствие logout при уничтожении экрана. Явная кнопка выхода сохранена.

## Доступ к фискальным документам

Проверенная реализация установленного SDK v0.6.03 читает `ReceiptApi.getFiscalReceipts` через URI `content://ru.evotor.framework.document.fiscal/receipt`. В исходном AndroidManifest этот отдельный authority не был объявлен в queries (были inventory и v2.receipt). 0.9 добавляет точный authority, без QUERY_ALL_PACKAGES и без новых сетевых прав. Это устраняет найденный пробел видимости на Android 11+; подтверждение, что именно он вызвал пустой ответ на конкретной кассе, требуется после обновления.

Перед запросом проверяется видимость провайдера. Сообщения различают отсутствие сервиса и null-ответ доступного сервиса. Null/исключение по-прежнему не означает «нет оплаты»: повтор блокируется до подтверждённого чтения. В настройках есть «Диагностика доступа к чекам». История попыток, UUID, nonce, digest, проверки текущего чека, оплат и исходных заказов не ослаблены; на сервере ничего принудительно не сбрасывалось. Подписка на широковещательные события удаления как обход проверки оплаты не вводилась.

## Сохранённый вход

После одного входа существующий Firebase refresh token шифруется AES-GCM с новым IV при каждой записи и AAD, привязанным к этому приложению. Ключ создан в Android Keystore, зашифрованный конверт лежит в private SharedPreferences; резервное копирование приложения уже отключено. Пароль и ID token не сохраняются. При запуске сохранённый refresh token обменивается на новый ID token; ротация refresh token сохраняется до принятия нового сеанса.

Временный сетевой сбой или HTTP 503 оставляет зашифрованный сеанс и показывает повтор восстановления. Отказ сервера обновления токена HTTP 400/401/403 удаляет сохранённый сеанс и требует пароль. Ошибка расшифрования или потеря ключа требует одного нового входа. Явное «Выйти из аккаунта» удаляет сохранённый refresh token и очищает данные входа в памяти; журнал чеков не удаляется. Сеанс даёт текущему пользователю кассы доступ к приложению до явного выхода/отзыва — это запрошенный пользователем режим.

Нет автоматического повтора SDK-команд или условных PUT после ошибок авторизации. Изменения не относятся к runtime сайта или Firebase Rules.

## Проверка

Регрессионные тесты проверяют наличие authority в manifest, запрет считать null нулём документов, восстановление после нового экземпляра, ротацию, явный выход, временный сбой и отзыв токена, отказ сохранения, AES-GCM round trip, разные IV, повреждение/усечение и неверный ключ. Работу конкретного Android Keystore и ответ провайдера проверяют после установки на физическую кассу.

Обновление: установить 0.9 поверх 0.8 без удаления данных; войти один раз. Затем проверить Home → запуск и удаление неоплаченного тестового чека → возврат к сохранённому счёту. Если провайдер остаётся недоступным, использовать диагностику, а не очищать данные или принудительно создавать дубль.

Источники: [Android package visibility](https://developer.android.com/training/package-visibility/declaring), [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [Firebase sessions](https://firebase.google.com/docs/auth/admin/manage-sessions), установленный integration-library v0.6.03 (`ReceiptApi`, `FiscalReceiptContract`, `FiscalDocumentContract`).
