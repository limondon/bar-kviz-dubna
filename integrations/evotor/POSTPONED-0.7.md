# Отложенные неоплаченные счета — APK 0.7

Рабочий сценарий: создать чек стола 4, отложить расчёт по просьбе гостя, рассчитать другой стол, вернуться к столу 4. Исходный прототип ошибочно трактовал любое уже выполненное открытие как окончательную одноразовую передачу. В 0.5–0.6 восстановление ограничивалось пустым/удалённым черновиком и предлагало возвращаться по кругу, когда исторический документ сохранял позиции, а текущий чек был уже другим.

## Действия сотрудника

1. Если счёт ещё открыт в «Продажа», в нашем списке нажать его строку и «Продолжить счёт»: откроется тот же UUID, без создания копии.
2. Для отложения нажать «Отложить счёт». Приложение сообщает, что состав уже сохранён, и переводит к этому заполненному чеку. В «Продажа» сотрудник вручную очищает неоплаченный черновик, освобождая кассу. Приложение не выполняет очистку, оплату или печать.
3. Рассчитать другой стол обычным способом.
4. Вернуться в «Счета с сайта», выбрать первый стол и нажать «Продолжить счёт». Если исходный чек не активен, платежей/фискальных документов нет и касса свободна, приложение готовит сохранённый состав для повторной проверки и отдельного подтверждения открытия.
5. При дозаказе, изменении визита, цены либо оценочных ценах старого заказа приложение требует обновить состав на сайте. Оно не угадывает новые позиции и цены.

## Проверка состояния

`ReceiptApi.getReceipt(context, uuid)` читает прежний документ; `getReceipt(context, SELL)` — текущий. Исторические позиции и номер сами по себе не означают оплату или текущую активность. Для решения используются отдельная привязка UUID к локальному журналу, успешное чтение платежей и фискальных документов, а также фактический текущий UUID и его заполненность.

| Состояние | Доступное действие |
| --- | --- |
| Исходный неоплаченный чек активен | Продолжить существующий чек; показать инструкцию отложения |
| Исходный не активен, платежей/фискальных документов нет, касса свободна | Подготовить сохранённый счёт к повторному открытию |
| На кассе другой заполненный чек или платёж | Сначала завершить работу с другим чеком; он не заменяется |
| У исходного есть платёж или фискальный документ | Повторное создание недоступно |
| Ошибка чтения или нет совпадающего локального журнала | Продолжение недоступно; показ причины и обновление состояния |

## Протокол

- Используется совместимое с сайтом состояние `cleared`, но история попытки отмечается `kind: postponed`. Переход условный по ETag; прежний nonce/UUID/digest сохраняются в `clearedAttempts`. Неизвестная попытка не переводится в отложенную.
- Если сайт уже прислал новую очередь, обновление на терминале её не перезаписывает. Повтор после потери подтверждения идемпотентен.
- Для самостоятельного освежения неизменённого снимка терминал проверяет открытый исходный визит, точное соответствие всех строк актуальным заказам дня, сохранённые цены каждой строки, актуальные карточки и их стоимость. Только после этого условный PUT переводит `cleared` в `queued` и обновляет timestamp. Для оценочных цен это запрещено.
- Перед SDK-командой повторно действуют проверки старого чека, свежести, текущего чека, состава, карточек и серверное резервирование. Запоздалый ответ старой попытки не перезаписывает новую. Частичная оплата и дозаказ после активного чека не считаются продолжением без изменений.
- Никаких сбросов живых передач из инструментов разработки и новых прав Firebase нет. Сайт v16 сохраняет историю `clearedAttempts`; изменения его runtime для 0.7 не требуются.

## Проверка на терминале

Unit tests проверяют переходы, запрет повторного создания при оплате/фискальных документах, сохранность другого чека, границы цены, конкурирующий ETag и потерянное подтверждение. Полный сценарий на физическом терминале требуется после установки 0.7 поверх 0.6 с сохранением данных приложения. Автоматической команды «припарковать текущий чек» в используемом SDK v0.6.03 нет; шаг ручной очистки в «Продажа» явно показан сотруднику.
