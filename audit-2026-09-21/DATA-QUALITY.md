# Разбор старых данных перед переносом — 21 сентября 2026

## Что проверено

Проверен полный экспорт рабочей Realtime Database, полученный 20 сентября только для чтения. Рабочая база не изменялась. Экспорт содержит 393 заказа, 217 записей столов и 651 строку заказа. Для воспроизводимости добавлена команда `node scripts/summarize-data-quality.cjs`; подробная машинная сводка сохраняется в закрытом от Git каталоге `.release`.

Этот снимок нельзя использовать как окончательный экспорт для публикации: после его получения рабочее приложение могло принять новые записи. Перед переносом проверка выполняется заново на свежем экспорте.

## Главный вывод

Потерь, дублей и нарушений целостности переноса не найдено. Проблема находится в неполноте старого формата: исторические заказы часто не содержат зафиксированную цену, итог и постоянный идентификатор товара. Автоматически подставлять современные цены нельзя — это изменило бы историю чеков.

Текущая подготовка v2 безопасно переносит все 393 заказа без изменения. Только 11 полностью самодостаточных заказов можно сразу вынести в обычный архив; 382 остаются в рабочем наборе, потому что архиватор намеренно отказывается скрывать неполные записи.

Окончательный вывод нужно делать по свежему экспорту непосредственно перед переносом.

## Практическое влияние

- Новые заказы после перехода будут содержать цену, итог и `productId`, поэтому эта проблема не будет накапливаться дальше.
- Старые неполные чеки сохранятся и будут доступны, но большинство из них не сможет автоматически перейти в строгий архив.
- Если оставить 382 записи в `live`, система останется корректной, но первоначальный рабочий набор будет больше запланированного.
- 12 заказов без совпавшей сессии нельзя автоматически приписывать другому столу или гостям.
- Исправление старых цен по сегодняшнему меню недопустимо: цена и состав меню могли измениться.

## Безопасное решение

Перед публикацией нужен свежий экспорт и повторная сводка. После этого старые полностью выданные записи можно хранить в отдельном режиме «наследуемый архив»: копировать исходный заказ без переписывания цены и итога, помечать неполные поля и не использовать такой чек для пересчёта склада. Это позволит убрать исторические записи из рабочих транзакций без выдумывания данных.

До реализации такого режима текущая стратегия остаётся безопасной: сомнительные записи сохраняются в `live`, ничего не удаляется и не пересчитывается автоматически.
